# Front-end plan

For the teammate who builds the front end, and for the people who review it.

## 1. What we are building

The Peekbox website, front end only: pages, styles and the code that makes them work in the browser. There is **no server and no database**. The sample data comes from the files in `content/data/`, and what a visitor does (their hamper, language, theme, orders) is kept in the browser.

- **Tools:** plain HTML, plain CSS and TypeScript. **No framework.** Do not add libraries without asking.
- **Look:** the mockups in `design/mockups/` (start with `customer/`). Read `design/design-notes.md` for colours and rules.
- **What each page must do:** `docs/functions.md` (the F-numbers), `docs/use-cases.md`, `docs/sitemap.md`.
- **Decisions already made:** `docs/decisions.md`. If a mockup and that file disagree, ask.

**Who does what.** You build the pages, one small slice at a time. The owner and the assistant review each slice and tell you what to fix. The base (milestone M0: the helpers, styles and tests) is already written. Mistakes are normal: the review is there to catch them, and nobody expects perfect code.

## 2. Setting up (once)

1. Install Node 22 or newer, and Git.
2. Get the project: `git clone https://github.com/quaint666/peekbox.git`, then open the folder.
3. `npm install`
4. `npm test`: you should see `pass 26` (or more) and `fail 0`.
5. `npm run dev`, then open http://localhost:3000 in the browser. You should see the Peekbox header, a line saying 24 sample products loaded, and the footer.
6. In a second terminal, run `npm run watch`. It recompiles your TypeScript every time you save. Leave it running while you work.

If the page shows an error about data, run `npm run build` once. If the browser seems to show an old version, do a hard reload (Ctrl+Shift+R).

## 3. How the project is organised

```
public/                  what the browser loads
  index.html ...         one HTML file per page
  css/tokens.css         colours, sizes, fonts: ALL the design values
  css/base.css           the plain look of HTML elements
  css/components.css     buttons, cards, form fields, header, footer, toast
  css/<page>.css         the layout of ONE page (you add these)
  images/  fonts/        pictures and the font
  js/                    GENERATED by the build, never edit, never commit
  data/                  GENERATED copy of content/data, never edit, never commit
src/                     the TypeScript (you write this)
  lib/                   shared code, already written (see below)
  pages/<page>.ts        the script of ONE page (you add these)
  i18n/vi.ts en.ts       interface text in both languages
content/data/            the sample data (products, packaging, campaigns)
tests/                   automatic checks, run with npm test
```

**Shared code in `src/lib/`** (use it, do not copy it):

| File | What it gives you |
|---|---|
| `config.ts` | Values the whole site shares: the 7-day margin, quick budgets, storage keys, event names |
| `data.ts` | `loadProducts()`, `loadPackaging()`, `loadCampaigns()`. The only way to get data |
| `pricing.ts` | `formatVnd()`, `isInDate()`, `quote()`, `itemStatus()`: all money and expiry maths |
| `search.ts` | Accent-free search |
| `hamper.ts` | `getHamper()`, `saveHamper()`, `withQty()`, `hamperCount()` |
| `i18n.ts` | `t('key')` for interface text, `localized(item, 'name')` for data text |
| `theme.ts` | Light and dark |
| `shell.ts` | `initShell('page')` draws the header and footer; `showToast()` |
| `dom.ts` | `h()` builds elements safely, `qs()` finds them, `icon()` draws icons |
| `storage.ts` | Safe saving to the browser |

## 4. The rules

Each rule exists because breaking it cost us time in an earlier project (Bloomy). `npm test` checks several of them for you.

1. **No inline styles, no inline scripts, no `onclick="..."`.** The page has a security policy that blocks them. Use CSS classes and `addEventListener`. If the console says "Content Security Policy", this is why. Do not weaken the policy.
2. **Never write `innerHTML`.** Build elements with `h()` or set `textContent`. Text that comes from data or from a visitor must never be treated as HTML.
3. **One place for each value.** A number, a colour, a name or a piece of text is written once, in `config.ts`, `tokens.css`, a dictionary or the data. If you type the same thing twice, stop and ask.
4. **Shared things are built once.** Header, footer and buttons already exist. Never copy them into a page. A style used by two pages goes in `components.css`; a style for one page goes in that page's CSS file.
5. **Money maths only in `pricing.ts`.** No price, total or budget calculation anywhere else.
6. **Data only through `data.ts`.** Pages never call `fetch` for data themselves.
7. **To hide something, use the `hidden` attribute.** The rule in `base.css` makes it really hide. Do not remove that rule.
8. **Colours and sizes come from `tokens.css` variables**, for example `var(--color-text)`. No new hex colours in other files.
9. **Both languages, from the start.** Visible text comes from `t('key')` or `localized(...)`. When you add a key to `vi.ts`, add the English one to `en.ts` (the build fails if you forget).
10. **Check every page at 1440 px and 390 px wide, in light and dark, in Vietnamese and English.**
11. **Do not animate from invisible.** Start at 40% opacity or more, never 0.
12. **Orders: once placed, clear the cart and disable the button.** The Back button must never place a second order.
13. **One scroll offset.** `base.css` already has it for `#anchors`. Do not add another.
14. **Small steps.** One pull request, one purpose, about 300 lines or fewer.
15. **Say what you did not test.** In every pull request, honestly.

## 5. How to build a page

1. Copy `public/index.html` to `public/<page>.html`. Keep the security policy line, the three style sheets, `theme-init.js`, the three `<div>`/`<main>` ids, and change the title and the script at the bottom.
2. Create `src/pages/<page>.ts` and start it with `initShell('<nav key>')`. Look at `src/pages/home.ts`: it is the pattern.
3. Get data with `data.ts`, draw the page with `h()`, and draw it again when the language changes (`EVENTS.languageChanged`).
4. Layout CSS goes in `public/css/<page>.css`, linked after `components.css`.
5. Open the matching mockup next to your page and compare.
6. Run `npm test`. Fix what fails.

**Simulated admin (M6).** There is no server, so the login is fake, the credentials sit in one clearly marked place in `config.ts`, and the orders and items live in the browser. The admin shows the orders that were placed on the customer side. Add a "reset demo data" button. The report must say plainly that login and 2-step code are simulated.

## 7. Pull requests and review

1. Make a branch for your slice, commit in small steps, push, and open a pull request. Use the front-end template (`.github/PULL_REQUEST_TEMPLATE/frontend.md`; GitHub offers it when you add `?template=frontend.md` to the new pull request address).
2. Put screenshots next to the mockup: 1440 px and 390 px.
3. The reviewers read the code and run it. They will tell you what to fix, as a list. Fix it on the same branch; the pull request updates by itself.
4. When the owner approves, it is merged as one commit.

**What a reviewer checks:** the build and tests pass; the rules in section 4; a hard-coded value or colour; text without a translation; the keyboard (Tab, Enter, Escape); the page in both themes and both widths; what the author said they did not test; and that nothing was added to the page that is not in `docs/functions.md`.

## 8. When something goes wrong

| You see | It usually means |
|---|---|
| "Content Security Policy" in the console | An inline style, script or event attribute was used. Use a class and `addEventListener` |
| "Element not found: #something" | The HTML does not contain that id, or the script runs on the wrong page |
| Data does not load | Run `npm run build` once; check that `npm run dev` is running |
| Old behaviour after you changed the code | Check `npm run watch` is running; hard reload |
| TypeScript error about a missing key in `en.ts` | You added a key to `vi.ts` only |
| A test in `seams.test.mjs` fails | You broke one of the rules in section 4; the message says which |

Ask early. A 5-minute question is cheaper than a day in the wrong direction.

## 9. For the report

While you build, keep: a screenshot of each function working (name the file by its F-number), and the function of code that does the work. The report needs, for each F-number: what it does, a screenshot of it running, and the code excerpt that handles it with a short explanation.

## 10. Not in scope

A real server, real payments, real accounts, a database, and any framework. If one of these starts to look useful, raise it first: it is a decision, not a task.
